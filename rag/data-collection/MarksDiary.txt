Start of the Mark Training:

The goal
Build a corpus of public-domain material about and by Mark Twain — substantial enough and clean enough to feed into a Retrieval-Augmented Generation system. The corpus needed to be diverse (different kinds of sources, not just one), well-attributed (every chunk traceable back to its origin), and reproducible (the build pipeline itself should be runnable from scratch by anyone).
The four sources
Each of these holds Twain-related material, but each uses a different access pattern. That diversity is part of the lesson: in any real corpus-building project, the sources don't conform to one shape.
Project Gutenberg — the canonical English-language editions of Twain's works (the novels, the autobiography volumes, the seven-volume Letters, the speeches, the essays). About 50 works, ~20 MB. We started from a curated index page edited by David Widger that organizes Twain's PG output into a clean bibliography. The same script also handles PG's "subject" pages, which is how you find works ABOUT a person rather than BY them.
Wikisource — human-transcribed (not OCR'd) public-domain texts. Smaller volume but very clean. For "works about Twain", Wikisource doesn't use a category — instead, the author page has a hand-curated "Works about Twain" section. The script reads that section via the MediaWiki API and downloads each linked page (encyclopedia entries from the 1911 Britannica, 1879 American Cyclopædia, etc.; biographical sketches; obituaries from the NYT and SF Call).
Internet Archive — broad, mid-quality OCR of pre-1929 books and monographs. We queried by subject + date range, capped at 200 items to keep volume sane, and let IA's library handle the actual downloads. This is where you find the early 20th-century biographies of Twain, contemporary scholarship, etc.
Chronicling America (Library of Congress) — historic American newspaper pages mentioning him. This is where you get the reception side: lecture announcements, book reviews, the surge of obituaries in April 1910. Caveat: noisy. Many "mark twain" hits are tangential, OCR errors, or wire-service duplicates. Useful as RAG retrieval material, less useful as training data.
The architecture that made it manageable
Each of those four sources got its own downloader skill, but they all produce output in the same shared shape: one HTML file (or plain text, for sources without HTML) + a .txt sidecar + a .meta.json sidecar following a common schema (id, source, source_url, title, author, date, category, file, text_file, bytes_text, fetched_at). A downstream aggregator walks the corpus directory, finds every .meta.json, and produces one unified corpus.json index.
The benefit: the RAG ingester doesn't need to know that source A used MediaWiki and source B used a custom library. It just iterates one schema. Adding a fifth source later (HathiTrust, Mark Twain Project, etc.) means writing a fifth downloader that emits the same sidecar shape — no plumbing changes downstream.
Polite by default. Every script identifies itself with a User-Agent that includes contact info, paces requests with a configurable delay (1–1.5s default), backs off exponentially on 429/503, and respects rate limits. Public archives like PG and Wikimedia treat polite clients well; aggressive ones get IP-banned.
Resumable everywhere. Each script writes a small state file as it works. Crash mid-run, restart, pick up where you left off. This matters when individual phases run for hours.
Idempotent. Chunk IDs in the embedding phase are deterministic (UUID5 of filename:chunk_index), so re-running any phase overwrites the same vectors rather than creating duplicates.
The two-phase ingestion
Once the corpus is on disk, getting it into Qdrant is a separate problem with separate failure modes. Embedding is CPU-bound and local; uploading is network-bound and cloud. Mixing them in one script means one timeout kills both.
So we split into two scripts:

embed_corpus.py — pure local. Chunks each text into 500-word pieces, embeds each chunk via a sentence-transformer, writes vectors.jsonl (one JSON line per chunk). With the HuggingFace cache populated and TRANSFORMERS_OFFLINE=1, this phase runs completely offline.
upload_vectors.py — pure network. Reads vectors.jsonl, batches into 250-vector upserts, pushes to Qdrant with retries. Resume tracks the line offset, so a network blip costs you one batch, not the whole upload.

The numbers

~189 source files in the corpus (after all four sources, deduped)
~50 books from PG canon (~20 MB), ~30 Wikisource pages, ~150-200 IA items (variable), ~500 newspaper pages
~18,000 expected chunks at 500 words each
~300 MB of vectors at typical embedding dimensions
Embedding throughput: ~1.8 chunks/sec on CPU; could be 10× faster with batch encoding or GPU
Total pipeline runtime: hours for embedding, minutes for upload

Lessons worth landing in the lecture
APIs decay. Halfway through this project we discovered Chronicling America had migrated to a new endpoint in August 2025; the old URL just 404s now. Your pipeline needs to assume any external dependency will change shape, and your scripts should fail loudly enough that you notice (not silently silently produce empty results).
Conventions vary by source. We initially guessed Category:Works about Mark Twain on Wikisource — doesn't exist. The actual convention is a section on the author page. There's no universal pattern; you have to learn each archive's idioms.
Heuristics misfire. The PG downloader's "use h1-h4 headings as category folder names" rule grabbed an h3 instruction line ("Click on the ## before each title…") and turned it into a 99-character folder name. Fix was a one-line restriction to h1/h2 only — but the lesson is that auto-categorization on heterogeneous documents always has edge cases.
Separate concerns aggressively. The two-phase embed/upload split, the per-source skills, the shared sidecar schema, the configurable contact info, the env-driven secrets — all are instances of "make each piece small enough that you can fix one without touching the others." When the network failed mid-upload, that didn't cost us any embedding work. When the PG folder names came out ugly, fixing them didn't require re-downloading anything.
Open-source-friendly defaults. Placeholders for contact info, secrets in .env.local (gitignored at repo root), modular scripts that work standalone or as Cowork skills. The same code can run in a researcher's notebook or in a teaching demo without changes.
